## Название и цель проекта

«Итоговый To-Do» — Android-приложение для ведения списка задач. Цель проекта — собрать в одном приложении изученные подходы: декларативный интерфейс Compose, навигацию, MVVM со StateFlow, локальную базу Room и сетевую загрузку через Retrofit.

## Технологический стек и обоснование

Приложение написано на Kotlin. Jetpack Compose и Material 3 используются для экранов; Navigation Compose переключает главную страницу, список и детали задачи. ViewModel объединяет состояние списка, фильтр, строку поиска и результат сетевого запроса в StateFlow. Room хранит задачи на устройстве и выдаёт наблюдаемые Flow. Retrofit с kotlinx.serialization загружает демонстрационные записи JSONPlaceholder.

Такой стек соответствует варианту 1 задания и использует Android-инструменты, изученные в лабораторных работах. Локальная база остаётся источником списка: интерфейс показывает сохранённые записи, а сетевой импорт обновляет только примеры.

## Реализованные функции

- Главный экран с количеством всех, активных и завершённых задач.
- Список с поиском по названию и тремя фильтрами состояния.
- Переход к деталям задачи, создание, редактирование, удаление и переключение статуса.
- Загрузка до 20 задач с `https://jsonplaceholder.typicode.com/todos`.
- Сохранение импортированных примеров в Room и повторное отображение после перезапуска.
- Обратная связь при сетевой ошибке с сохранением доступа к локальному списку.

Запрос JSONPlaceholder работает только на чтение. Изменения пользователя остаются в локальной базе и не синхронизируются с удалённым API.

## Архитектура

```text
Экраны Compose
      ↕ действия / StateFlow
TaskViewModel
      ↕
TaskRepository ───────── Retrofit / JSONPlaceholder
      ↕                         │ импорт DTO
TaskDao / Room  ←───────────────┘
```

`TaskViewModel` принимает действия UI и держит состояние экрана. `TaskRepository` координирует источник данных и преобразует сетевые DTO в локальные сущности. `TaskDao` предоставляет Flow для чтения и suspend-операции для записи. Экран подписывается на StateFlow через lifecycle-aware сбор состояния.

## Трудности и решения

Сетевой источник может быть недоступен, поэтому приложение не должно зависеть от успешного запроса, чтобы показать задачи. Данные читаются из Room, а Retrofit работает как дополнительный импорт. Ошибки HTTP и отсутствие соединения преобразуются в понятное сообщение; локальный список при этом остаётся доступным.

При изменении задачи UI должен обновляться без ручного перезапроса. Для этого Room выдаёт Flow, а ViewModel комбинирует его с состоянием поиска, фильтра и сетевого запроса в StateFlow.

## Рефлексия

В проекте я закрепил связь между слоями UI, ViewModel, Repository и DAO, а также увидел, как реактивный поток базы упрощает обновление интерфейса. Отдельно стало яснее, что локальное хранение и серверная синхронизация — разные функции: текущая версия загружает публичные примеры, но не отправляет изменения пользователя обратно.

## Ограничения и дальнейшее развитие

В этой версии нет учётных записей, удалённого создания и редактирования, автоматической фоновой синхронизации и unit-тестов. При дальнейшем развитии можно подключить собственный API с авторизацией, добавить фоновые повторы через WorkManager, покрыть Repository и ViewModel тестами и реализовать категории задач.
